Executive Summary

Govt. Graduate College, Mandi Bahauddin runs its academic life on paper. Roughly 3,000 students across Intermediate and BS programmes, and about 50 faculty members, still queue at the accounts window for a fee challan, wait for a hand-written attendance register to be tallied, and read their semester result off a notice board instead of a phone. Every one of those steps is somewhere a form can go missing, a number can be mistyped, or a student simply doesn't find out in time, a wrong CGPA on a transcript, a challan that doesn't match what the accounts office has on file, an exam schedule that reaches half the class.

The system we built is six applications, not one. There is an admin app, a teacher app, and a student app, and each ships both as an Android phone app and as a Compose-for-Desktop app. All six sit on a single shared Supabase database and draw from one shared component library, the "Modernist" red/ink design system, so a student's attendance, a session's fee structure, or a published datesheet is the same record no matter which app opens it, on either platform. The admin side holds the college's structure: departments, the academic sessions inside them, and each session's curriculum, timetable, and fee heads. Teachers work against that same structure, marking attendance, entering midterm and sessional marks, submitting exam papers, and recording semester GPA/CGPA. Students see only their own slice of it, attendance, marks, fee challan, datesheet, and calendar notices, without walking into an office.

The reason so much of this works cleanly is that the access rules live in the database, not in the apps. Postgres on Supabase stores everything; Row-Level Security decides who can read and write each row; GoTrue handles sign-in; and Storage holds uploaded files such as exam papers. That was a deliberate switch away from an earlier Firebase/Firestore prototype, and the payoff is the guarantees a relational schema gives that a document store could not, a mark cannot be attributed to a student who was never enrolled in that session, and a fee record cannot outlive the session it belongs to, because foreign keys and row-level policies refuse to let it. The apps are Jetpack Compose on mobile and Compose for Desktop on the desktop, both built on the same MVVM/Repository split and wired with Hilt, which is what lets all six share one component library rather than maintaining six separate sets of screens.

What this report describes is the system as it stands in the codebase. Its spine is a department-centric academic structure with per-session fees and a lock-then-approve workflow for marks: a teacher enters a score once, and changing it afterward requires an admin's sign-off through a mark-correction request. Around that sit semester results with GPA/CGPA and supply-subject tracking, fines, a calendar, datesheets, and a tiered Insights view built on Postgres views, an admin sees the college-wide figures while a teacher sees only their own classes, and that scoping is the database's own row-level rules doing the work, not extra logic in the app. All six applications build and run against the live Supabase project.

1.1 Problem Statement

Govt. Graduate College, Mandi Bahauddin runs on paper. Around 3,000 students across its Intermediate and BS programmes, and roughly 50 faculty members, depend on class registers, printed notices, and trips to administrative offices for work that repeats every term. Attendance sits in a register until someone tallies it by hand, so a student's real standing is not known until the counting is done. Marks and semester results move through several paper steps, which makes them slow to check, slow to correct, and slow to share, and easy to get wrong, whether that surfaces as a mistyped CGPA on a transcript or a fee challan that does not match what the accounts office has on file. Timetables, examination dates, and notices live on a noticeboard, so a student who is absent or simply does not walk past it can miss them; an exam schedule that reaches only half the class is a real outcome here, not a hypothetical. For anything about fees, fines, results, or schedules, students often have to come to campus and stand at a window to ask. Teachers carry their own version of this, copying the same figures once into the class record and again into an administrative report. The administration's difficulty is that the picture is scattered: departments, academic sessions, teachers, and students each sit in separate records, so assembling a complete report means comparing registers by hand, and a correction made in one place rarely reaches the others. Paper is also hard to search and no use at all to anyone away from campus. None of this is unusual for a college of this size, it just grows heavier as the number of students, classes, and activities increases. What is missing is a single coordinated system that administrators, teachers, and students can each work in, and see only their own part of, from either a phone or a desktop.

1.2 Problem Solution

The answer is one College Management System split across six applications: an admin, a teacher, and a student app, each built for both a phone and a desktop. They are less six separate programs than six views of the same college records. Everything sits in a single shared database, so a figure entered once by whoever is responsible for it becomes the record everyone else works from, instead of being written down a second time in another register. That alone removes most of what makes §1.1 painful, the manual re-tallying, the correction that never reaches the other book, the report assembled by comparing registers side by side. Sign-in establishes who you are and opens only your part of the system, and that boundary holds all the way down to the data: each role can read and change exactly what it is allowed to and nothing more, because the database itself enforces the rule rather than trusting each app to behave.

The admin apps hold the college's structure and oversight, departments, academic sessions, students, teachers, other administrators, timetables, fees, attendance reports, examinations, and notices. The teacher apps cover the daily academic work: viewing assigned classes, marking attendance, entering marks, submitting examination papers, checking schedules, and requesting a correction when a recorded mark has to change. The student apps give each student a clear read on their own attendance, timetable, marks and results, fee challan, datesheets, and notices, and let a newly registered student ask for their account to be linked to the correct college record.

The two formats are meant to complement each other, not fork into separate procedures over separate data. A phone is what a teacher has in hand during class and what a student has when away from campus; the desktop gives the same role-based work a larger screen for office data entry and printing, such as generating a fee challan. Where an action carries weight, changing a mark that was already recorded, or approving a student's link request, it runs through a visible approval step rather than a silent edit. That is what keeps the records trustworthy, not just quicker to produce. Taken together, the aim is straightforward: college information that is easier to keep correct, faster to reach, and dependable for administrators, teachers, and students alike.

1.3 Objectives of the Proposed System

Each objective below is concrete enough to check against the finished system:

  • Ship six working applications, a mobile and a desktop app each for administrators, teachers, and students, all running against the same college database.
  • Hold a single authoritative record for every department, academic session, subject, teacher, student, timetable, attendance entry, mark, semester result, and fee structure, so the same value is never entered twice.
  • Let an authorised teacher record a full class attendance register on screen instead of on a paper register, and make that register visible to the administration and to the affected students once it syncs.
  • Route every change to an already-recorded mark through an administrator's approval, so a submitted score cannot be altered silently.
  • Record semester results, including GPA, CGPA, and supply (repeat) subjects, against the enrolled student rather than on a separate sheet.
  • Give each student their own attendance, timetable, marks, results, fee challan, fines, datesheets, and notices on their own device, so routine questions no longer require an office visit.
  • Publish notices, calendar events, and examination datesheets to the roles they are meant for, on both mobile and desktop.
  • Show administrators live summaries of departments, sessions, teachers, students, attendance, and academic performance drawn straight from the records rather than compiled by hand, with a teacher's view scoped to their own classes by the same rules.
  • Enforce role-based access throughout, so each user can see and do only what their role allows.
  • Keep the mobile and desktop version of each role consistent in content, navigation, and the main workflows.
  • Verify all six applications through functional and user-interface testing before final submission.

1.4 Scope

The system covers the everyday academic and administrative work of Govt. Graduate College, Mandi Bahauddin for three groups of people: administrators, teaching staff, and enrolled students. Each group has both a mobile and a desktop application, and both work on the same college records, so what a person can see and do depends on their role, not on the device in their hand.

In scope:

  • Setting up and maintaining the college's structure, departments, academic sessions, subjects, classes and offerings, teachers, administrators, students, and the requests students raise to link an account to their own record.
  • Class timetables and teacher schedules, examination datesheets, and college calendar events.
  • Attendance: teachers record a class register, students see their own attendance, and administrators read it back as reports.
  • Marks entry, administrator-approved mark corrections, semester results with GPA/CGPA and supply subjects, examination-paper submission, and the academic summaries built from all of this.
  • Session fee structures, per-student fee challans, fines, notices, and notifications.
  • Mobile and desktop access for all three roles, with the same information and role-appropriate actions on each.

Out of scope:

  • Online fee payment or any direct link to a bank. The system shows the fee structure and produces the challan; the student still pays at the accounts office.
  • Automatic grading of examination papers, or any software standing in for a teacher's academic judgement.
  • Public website features, online admissions, hostel management, payroll, and library circulation.
  • iPhone apps, browser-based access, and running more than one college from a single installation, the build targets Android phones and the desktop, for this one college.

1.5 System Components

The system presents six user-facing applications: an admin, a teacher, and a student app, each in a mobile (Android) and a desktop version. The two versions for a given role carry the same information and follow the same college procedures, only the layout changes to suit the screen, so the phone leans on compact cards and lists while the desktop spreads the same records into wider tables.

That consistency is not kept up by hand across six separate codebases. The apps stand on a shared foundation: a portable core module holds the domain model, the data-transfer objects, the repositories, and the authentication that every app relies on, and two platform kits build on top of it, mobile-shared (the Android UI kit, together with the local cache and dependency wiring the three phone apps use) and desktop-shared (the Compose-for-Desktop UI kit the three desktop apps use). Because the shared logic lives in one place, a rule written once holds everywhere it is applied, and each of the six apps is left to assemble its own screens from common parts.

The applications and their individual features are described in the subsections that follow.

1.5.1 Admin Mobile Application

The college's control panel in a pocket, the full academic structure plus the approvals and reports an administrator needs while away from the office desk:

  • Dashboard with the headline totals (students, teachers, departments), pending requests, recent notifications, and shortcuts into the common tasks.
  • Academic structure: departments and their detail, academic sessions, per-semester subjects (the curriculum), class rosters, per-session and master timetables, buildings and rooms, and each session's fee structure.
  • People: teachers and their individual permissions, other administrators, and student profiles, including issuing and tracking a student's fines.
  • Approvals: reviewing student account-link requests and teachers' mark-correction requests before either takes effect.
  • Records and reporting: attendance reports, an Insights view of academic summaries, submitted examination papers, and examination datesheets.
  • Communication: calendar events and notifications, both viewing them and sending them.

1.5.2 Admin Desktop Application

The same administrator, at a desk instead of on a phone, identical data and rules, laid out for a larger screen and the office work that goes with it:

  • Covers the same administrative areas and permissions as the Admin Mobile app, academic structure, people, approvals, attendance and records, the Insights summaries, calendar, notifications, and datesheets, all working on the same college data.
  • Lays those records out for a large screen: wide, multi-column data tables built for working through long lists of departments, sessions, teachers, students, and records without the constant scrolling a phone forces.
  • Adds the desk-bound work a phone handles poorly, exporting attendance and academic reports to CSV or PDF, generating and printing fee challans, and opening and saving files through the desktop's own file dialogs.
  • Keeps the approval steps, status labels, navigation order, and data identical to the mobile app, so moving between the two never changes the rules or the numbers.

1.5.3 Teacher Mobile Application

Built for a teacher's day, mostly attendance and marks, with the surrounding academic work kept close at hand:

  • Home with the next class, upcoming deadlines, recent notices, and shortcuts into the common tasks.
  • Attendance: mark a full class register for the day, and open the history to check or review earlier registers.
  • Marks: enter midterm and sessional scores; once a score is locked, request a correction that an administrator must approve rather than editing it directly.
  • Semester results: record a student's GPA, CGPA, and supply subjects for the term.
  • Examination papers: submit exam papers through the Exams hub.
  • Schedule and classes: the teacher's own timetable, the students assigned to them, the published examination datesheet, and college calendar events.
  • Insights, scoped to the teacher's own classes, the same kind of summaries the admin sees college-wide, limited to what this teacher is responsible for.
  • Notifications, plus reviewing student link requests and sending notifications where the administrator has granted those permissions.
  • Profile and account.

1.5.4 Teacher Desktop Application

The same teaching work as the mobile app, on a desk-sized screen for the parts that involve long lists and files:

  • Covers the same teaching responsibilities and access limits as the Teacher Mobile app, attendance and history, marks entry with locked-mark correction requests, semester results, exam-paper submission, schedule, assigned students, datesheets, calendar, the class-scoped Insights, and notifications, all on the same college data.
  • Uses the extra screen space for the list-heavy work: class rosters, attendance registers, marks-entry grids, schedules, and result review sit in wide tables rather than scrolling cards.
  • Handles the desk-bound file work, choosing and opening files, such as the PDF for an exam-paper submission, and printing where it is useful.
  • Keeps the teacher's classes, records, notices, and approval status identical to the mobile version, so nothing shifts when moving between the two.

1.5.5 Student Mobile Application

A student's own record in their pocket, reachable without an office or noticeboard visit:

  • Register and link: a student registers, then requests that the account be linked to their college record; the rest of the app stays gated until an administrator approves that link.
  • Home with the day's academic information, the next class, and recent notices.
  • Academics: personal attendance summary, timetable, marks, semester results (GPA/CGPA), the published datesheet, and the college calendar.
  • Fees: the fee challan, which the student can open and download as a PDF, with any fines shown on their profile.
  • Notifications and profile, the profile also carrying enrolment history.

1.5.6 Student Desktop Application

The student's own information on a full screen, with the printing the college still asks for on paper:

  • Shows the same personal academic and fee information as the Student Mobile app, attendance, timetable, marks, semester results, datesheet, calendar, fee challan, and notifications, with fines on the profile, behind the same account-linking gate.
  • Uses the larger display for easier reading of timetables, attendance history, results, and datesheets.
  • Handles the desk-bound file work: downloading and printing the fee challan, and saving or printing the student's own records where useful.
  • Keeps account and link status, notifications, and displayed information identical to the mobile version.

1.8 System Limitations and Constraints

Limitations, factors outside the team's control that bound what the system can do:

  • The apps need a network connection for anything live. Each app keeps a local cache and still shows its last-synced data when offline, but receiving the newest records and submitting new or changed ones both require connectivity.
  • Hosting and uptime depend on Supabase, the external service that stores and exchanges the college's data; an outage there is beyond the team's control.
  • The Android apps require Android 7.0 (API 24) or later, and the desktop apps need a Java-capable computer; older phones are not supported.
  • A report is only as accurate as what authorised users enter, the system cannot correct information it was never given.

Constraints, choices the team made deliberately:

  • The first release targets a single college and follows the academic practices of Govt. Graduate College, Mandi Bahauddin.
  • The apps are built for Android phones and a Windows desktop (on the JVM); iPhone and browser versions were left out of scope.
  • Fees are informational only. Students can see the fee structure and challan, but payment stays with the college's existing process, no payment gateway is integrated.
  • Examination papers are submitted and managed in the system, but grading stays with the teacher; there is no automatic marking.
  • The scope and depth of testing were bounded by the academic schedule, the team's size, and the devices and sample data available during development.

2.2 Requirement Identifying Technique

Because all six applications are interactive and role-based, the requirements were drawn out mainly through use-case modelling: each activity starts with a user goal, runs through an expected sequence, and ends in a result you can observe and later test. That framing keeps the requirements readable without asking the reader to know how the apps are built. The sections that follow show how it was applied, reviewing the college's existing processes and each role's responsibilities (§2.2.1), checking the ideas against a cross-platform prototype of the six apps (§2.2.2), writing the activities up as fully dressed use cases (§2.2.3), and summarising them as per-app use-case diagrams (§2.2.4).

2.2.1 Process and Stakeholder Review

The requirements grew out of how the college already works. Its existing paper-based procedures, and the records that move through them, were set against what each role, administrator, teacher, and student, is actually responsible for. Four questions drove the review: who creates a given record, who has to approve it, who may see it, and what should happen when information is missing or wrong. That last group is what later shaped the system's access rules and its input checks. The review split cleanly by role:

  • Administrative work, college structure, people management, approvals, fees, notices, reporting, and control over who is allowed to change what.
  • Teaching work, schedules, attendance, marks and locked-mark corrections, examination papers, results, student lists, and notices.
  • Student needs, registration and account linking, then a personal view of academic records, fee information, datesheets, and notifications.

2.2.2 Prototype and Cross-Platform Review

The screens were reviewed as working prototypes (collected in Appendix C) to check that every activity had a clear way in, understandable feedback, and a layout that made sense on both a phone and a desktop. The same pass surfaced the desktop-specific needs a phone does not have, choosing, opening, and saving files, exporting, and printing. Throughout, a role's mobile and desktop apps were treated as two ways into the same work, not two separate stores of college information: the desktop apps run on the same shared logic as their mobile counterparts, so a requirement satisfied on one platform is satisfied on the other rather than specified twice.

3. System Design

The College Management System is a family of six applications rather than one big interface: an admin, a teacher, and a student app, each on both a phone and a desktop, all sharing the same college records and business rules so that an action taken on one device shows up wherever that authorised information appears. Behind them sit managed services for accounts, the database, file storage, and email.

The rest of the chapter shows how those parts fit together, the design constraints and risks, the main information objects and how they relate, the architecture that ties the six apps to one backend, the data organisation, the user interfaces, the key interactions and workflow states, and the design decisions that keep mobile and desktop behaving the same.

The design was shaped by the college environment: people move between office computers and personal phones, the internet is not always steady, and access to student information has to follow each person's role. The main considerations, and the response built into the design, are below.

3.3 Architectural Design

The system follows a layered client-server design. The six apps present role-specific workspaces on top of shared services that apply the same validation, access rules, and record operations, so the college's rules are written once rather than in six places. The managed backend holds the accounts, the college data, and uploaded files such as exam papers and photos. Each app also keeps a role-scoped local copy of the records it is allowed to see: it builds that copy on first use, and later refreshes pull only what changed since the last successful sync and apply it in one step, enough for a useful view on a weak connection, without becoming a second source of truth, since the online database stays authoritative.

The sections that follow set out the system context (§3.3.1, the six apps around the shared backend), the component structure (§3.3.2, the core and platform modules that feed the six apps, Figure 3-3), and the architecture style with the module mapping (§3.3.3, a layered MVVM/Repository design wired with Hilt, Figure 3-4).

3.3.1 System Context

At the edges of the system are its three kinds of user; at the centre is one shared backend. Administrators and teachers create and update information within their authority, while students mainly view their own and published information, with a few actions of their own, registration, account linking, and profile upkeep. Whether a person is on a phone or a desktop, their app exchanges data with the same backend, so moving between devices never creates a separate record. That backend is the Supabase project: PostgREST serves the college records, GoTrue handles sign-in, Storage holds uploaded files, and a small set of service-role functions carry out admin-only operations, all reached over HTTPS, with Row-Level Security deciding what each signed-in user may read or write.

3.3.2 Component Structure

The code is organised into layers of components rather than six standalone programs. At the base sits the portable core module, the domain model, the data-transfer objects, the repositories, and the authentication logic every app shares. Two platform kits build on it: mobile-shared, the Android UI kit with the Room cache and the Hilt wiring the three phone apps use, and desktop-shared, the Compose-for-Desktop UI kit the three desktop apps use. The six app modules themselves are thin, each supplies its role's screens and assembles them from those shared parts. So a workspace in any app calls into a shared repository, which applies the identity, academic, publishing, and reporting rules before reaching the Supabase backend; the same rule runs the same way whichever app invoked it.

3.4 Data Design

Information is organised around stable college records rather than around individual screens. Departments and academic sessions form the structure; people records identify administrators, teachers, and students; teaching records hold timetables, attendance, marks, and results; publication records carry datesheets, calendar events, and notifications; and financial records cover fees and fines. All six apps read and update the same authorised record, so a mobile and a desktop version never drift into separate sources of truth.

The relationships are explicit. A student belongs to an academic session, a subject is offered in a particular semester, and every attendance or assessment entry carries enough context to pin down the exact class. Published information records the audience it is meant for, and an approval record keeps both the requested change and the decision made on it.

Records also carry creation and update timestamps, which is how a refresh finds the newest authorised version of a row and pulls only what changed. Deletions are tracked long enough for other devices to drop their local copy, and ordinary lists never show removed rows. In the admin apps, an information control on each saved record can show its creation and update details, without exposing deletion details to routine users.

4.1.1 Start and Route a Signed-In User

Every app runs the same startup check, so a user lands in the right place, or is stopped, without ever seeing something they shouldn't. It reuses a valid session where one exists, confirms the account's role and status before opening a workspace, and, for an administrator, kicks off the data preparation in Algorithm 2.

Algorithm 1: Start and route a signed-in user

  • Input: a saved account session and the selected role app
  • Output: the login screen, an access message, or the authorised role workspace
  • Cost: O(1), a few decisions and indexed account lookups
  1. Show the splash screen while the account check is in progress.
  2. Restore the saved session if one exists.
  3. If there is no valid session, open the login screen and stop.
  4. Read the cached role, then confirm the current role and account status from the account's profile.
  5. If the account is inactive, show an access message, clear the session, and stop.
  6. If the role does not match the selected app, show the correct-role message and stop.
  7. If the role is Administrator and the core data is not yet prepared, run Algorithm 2.
  8. Open the authorised home workspace and stop.

4.1.2 Prepare Administrative Data

When the Admin app opens, it loads the college's core reference data once in the background rather than fetching it screen by screen. The dashboard shows progress and whatever is already cached, so the administrator is never left on a blank page; later refreshes pull only the rows that changed.

Algorithm 2: Prepare administrative data

  • Input: the administrator account and its saved preparation status
  • Output: a ready workspace built on current or previously prepared data
  • Cost: O(D + T + S + R) over the departments, teachers, students, and supporting records loaded
  1. Start once the administrator role is verified.
  2. If preparation is already complete for this account, open the workspace and stop.
  3. If usable prepared data already exists, mark it ready, open the workspace, and stop.
  4. Show a preparation message and block duplicate preparation attempts.
  5. Request departments, sessions, teachers, students, timetable, approvals, and supporting records.
  6. Validate each returned group before it replaces the previously available data.
  7. If the essential groups load, remember completion for this administrator.
  8. If any request fails, keep the safe existing data and offer a retry.
  9. Open the administrative workspace and stop.

4.1.3 Validate a Timetable Period

Adding a period to a session's timetable has to avoid two clashes: the same teacher, or the same room, booked over the same time on the same day. The check runs in the app and, decisively, as a BEFORE trigger in the database, so a conflict is caught even if two edits race. Only lecture periods are checked; breaks, zero periods, and a merged lecture (one row serving several sessions) are exempt. Rooms are picked from the managed buildings-and-rooms lists.

Algorithm 3: Validate a timetable period

  • Input: session, day, start/end time, teacher, room, and effective dates
  • Output: the saved period, or a clear conflict message
  • Cost: O(P) over the P relevant periods on that day
  1. Start when a timetable period is submitted.
  2. If the start time is not before the end time, reject the period and stop.
  3. For each existing lecture on the same day whose effective dates overlap (a null date means unbounded):

a. If its teacher matches and the times overlap, reject with the teacher conflict and stop. b. If its room matches and the times overlap, reject with the room conflict and stop.

  1. Check that the session does not already hold the same slot.
  2. Save the period, attach any approved shared sessions (a merged lecture), confirm, and stop.

Time overlap is half-open, two periods clash when one starts before the other ends and vice versa.

4.1.4 Record Class Attendance

Only the teacher assigned to a class can record its attendance, the database's row-level rules enforce that, and an administrator can read the result but never write it. The teacher marks each student present, absent, or on leave, optionally flagging a present student as late, and the whole register is submitted in one go; a register already recorded for that meeting is opened for review rather than silently duplicated.

Algorithm 4: Record class attendance

  • Input: the assigned class, subject, date, roster, attendance states, late flags, and notes
  • Output: one confirmed attendance entry for every student in the class
  • Cost: O(N) time and space over N students
  1. Start after the teacher selects an assigned class and subject.
  2. Load the roster and any attendance already recorded for that date (open it for review if it exists).
  3. For each student, capture present, absent, or leave, plus an optional late flag and note.
  4. If any student's status is missing, point out who and stop without saving.
  5. Build one dated entry per student.
  6. Submit the complete register as a single operation.
  7. If it is confirmed, update the visible history and show success.
  8. Otherwise keep the teacher's selections and offer a retry.

4.1.5 Record Assessment Marks

A teacher enters marks for one subject and assessment type, midterm out of 25, or sessional out of 15 (its attendance, assignment, and quiz components of five each, summing to fifteen). A score must be a whole number within that maximum; anything blank, non-numeric, negative, or over the limit is flagged before submission. Once submitted, a mark is locked, and any later change is not a direct edit, it goes through the correction request in Algorithm 6.

Algorithm 5: Record assessment marks

  • Input: the assigned class, subject, assessment type, roster, scores, and absence selections
  • Output: confirmed first-time marks, or field-level correction messages
  • Cost: O(N) time and space over N students
  1. Start after the teacher selects an assignment and assessment type.
  2. Load the roster, any marks already recorded, and any pending correction requests.
  3. For each student without a locked mark:

a. accept "absent" or a whole-number score within the assessment maximum (25 for midterm, 15 for sessional); b. show a correction message for a blank, non-numeric, negative, or too-large value.

  1. If any entered value is invalid, keep the form open and stop.
  2. Save only the valid first-time marks and lock them once confirmed.
  3. Route any later change to Algorithm 6 (mark correction) and stop.

4.1.6 Review a Mark Correction

Changing a locked mark is a two-person job: a teacher raises a correction, and an administrator, never the same teacher, decides it. That is what keeps a submitted score from being altered quietly.

Algorithm 6: Request and review a mark correction

  • Input: the locked mark, the requested mark, a reason, the teacher's identity, and the administrator's decision
  • Output: an approved, updated mark, or a rejected request with the original retained
  • Cost: O(1) per request
  1. Start when a teacher selects a locked mark.
  2. Check the requested value is a whole number within the assessment maximum.
  3. If a request is already pending for this mark, show its status and stop, only one may be open at a time.
  4. Create a pending request holding the original value, the requested value, and the reason.
  5. Show it in the review list of an authorised administrator, who cannot be the teacher who raised it.
  6. If the administrator approves, apply the requested value to the mark and close the request as approved.
  7. Otherwise leave the mark unchanged and close the request as rejected.
  8. Record the reviewer and the decision time, a decided request cannot be decided again, refresh the affected view, and stop.

4.1.7 Link a Student Account

A registered student sees no academic data until their account is linked to a college record, the app stays gated until then. The student claims a roll number from the list of unclaimed ones in their session and adds identity details (CNIC/B-form, name, and date of birth); an administrator checks the claim against the roster and links exactly one account to one record, keeping a single live link per record.

Algorithm 7: Link a student account

  • Input: the registered account, the selected department and session, a claimed roll number, and supporting identity (CNIC, name, date of birth)
  • Output: an approved personal workspace, or a rejected request with a reason
  • Cost: O(S) over the S students in the selected session
  1. Start once student registration is verified.
  2. If the account is already linked, open the personal workspace and stop.
  3. If a request is already pending, show its status and stop.
  4. Let the student pick a roll number from the session's unclaimed list and submit it with their identity details as a pending request.
  5. An administrator reviews the request against the session's roster, seeing only the claimed roll and matching identity, not other students' details.
  6. If exactly one authorised record matches, link the account to it and mark the request approved; if that record was linked to another account before, downgrade the previous account's stale approval so only one live link remains.
  7. Otherwise reject with a clear reason and keep the academic records closed, the student may resubmit.
  8. Refresh the student's access state and stop.

4.1.8 Build a Student Academic Overview

A student's home brings everything about their own record into one view. It is assembled on the device from the base records the student is allowed to see, the same row-level rules that protect the data also scope it, rather than from a prepared server summary. Absent or unpublished values are shown as such, never as a misleading zero.

Algorithm 8: Build a student academic overview

  • Input: the approved student link and the current session
  • Output: a home summary, attendance, schedule, marks, results, fees, and notices
  • Cost: O(C + A + M + R) over the courses, attendance entries, marks, and result records used
  1. Start once the student account is linked.
  2. Load the student's current session, semester, subjects, and timetable.
  3. Load only that student's own attendance, marks, semester results, fees, fines, and the publications meant for them.
  4. Work out per-subject attendance percentages (against the 75% line) and find the next scheduled class.
  5. Take current standing, GPA, CGPA, and any supply subjects, from the latest completed result.
  6. For marks, show midterm out of 25, sessional out of 15, and the total, marking an unentered or absent value plainly rather than as zero.
  7. If one information group is unavailable, show the rest and a retry for the missing group.
  8. Present the same information in the mobile or desktop layout and stop.

4.1.9 Publish Information for an Audience

Most of what an administrator or teacher creates is meant for some people and not others: a datesheet for one session, a calendar event for a department, a notice for a single class, a fine against one student's fee record. The publisher never picks who can see an item by hand. They set what it is and who it is for, a role, and where it applies a department or a session, and the same row-level rules that guard the database decide, per reader, whether the item is returned at all. A datesheet is the one type that waits: it is saved as a draft and only reaches students once it is explicitly published. A calendar event, a notification, or a fee record is live to its audience the moment it is written.

Algorithm 9: Publish information for an audience

  • Input: the authorised publisher, the item type, its fields, and the target audience (role, and optionally a department or session)
  • Output: an item stored and returned only to the readers it is meant for
  • Cost: O(M) over the M records a given reader is entitled to list
  1. Start when an authorised administrator or teacher composes an item.
  2. Check the required fields for that type, a datesheet needs its session and slots, a calendar event its date, a notification its title and body, a fine its amount and the fee it attaches to.
  3. Confirm the audience is one the publisher may write to: an administrator across their department, a teacher within a class they are assigned.
  4. Write the item with its audience recorded on the row, the role it targets, and the department or session that scopes it.
  5. For a datesheet, hold it as a draft; it stays out of student view until the publisher marks it published. Other types are visible to their audience on write.
  6. When an app lists current items, the reader's own role and academic scope are applied by the row-level rules before anything is returned, no client-side filtering stands between a reader and a record they should not see.
  7. Show an empty list as empty, and tell it apart from a request that failed.
  8. Let the publisher amend or withdraw an item within the same authority that let them create it, and stop.

4.1.10 Complete a Desktop File Action

On the desktop apps a user can take a record they are already looking at and turn it into a file on their own machine, a CSV or PDF of an attendance report or roster, or a printable fee challan. The app builds the file in memory, hands the operating system a native dialog to pick where it goes or which printer prints it, writes or prints the result, and opens it in the default viewer. None of this changes anything in the college database; an export only reads what the signed-in role is already allowed to see, so a cancelled or failed action leaves the records exactly as they were.

Algorithm 10: Complete a desktop file action

  • Input: the record on screen, the chosen action (save, print, or share), and the destination the OS returns
  • Output: a saved, printed, or opened file, or a clean cancellation, with college data untouched either way
  • Cost: O(F) over the F bytes of the file; the source records are already loaded
  1. Start when a desktop user chooses to export, print, or share what is on screen.
  2. Build the payload from the loaded records, a CSV or PDF report, or a three-copy challan PDF. The data was fetched under the role's own access rules, so nothing outside that scope can enter the file.
  3. Open the matching native dialog: a save-file dialog for an export, the OS print dialog for a print, the default handler for a share.
  4. If the user cancels the dialog, stop, no file is written and no college data changes.
  5. Write the file to the chosen location (or send it to the selected printer), then hand it to the OS so the default viewer opens it.
  6. If the OS action succeeds, show the confirmation.
  7. Otherwise report it in plain language, no permission for that folder, the printer is unavailable, the file could not be written, and stop.

4.2 External APIs/SDKs

The six apps lean on a small, deliberately shared set of libraries rather than a different stack per platform. Everything to do with the backend, sign-in, reading and writing records, files, and the privileged server operations, goes through one client: the Supabase Kotlin SDK, version 3.1.4, pulling in its PostgREST, Auth (GoTrue), Storage, Realtime, and Functions modules from a single BOM. That SDK runs on Ktor 3.1.1 for the actual HTTP, and Kotlinx Serialization 1.8.0 turns records into JSON on the way out and back. There is no Firebase or FCM anywhere in the project; notifications are rows the apps read under their own access rules, not a push service.

Above that, the split is only where it has to be. The three phone apps draw their screens with Jetpack Compose (Material 3), the three Windows apps with Compose Multiplatform (Material 3), the same declarative model, two runtimes. Both sides cache their data with Room so a workspace reopens with its last good records offline; the desktop build sits on a slightly newer Room (2.8.4) with the JVM bundled SQLite driver because it targets plain JDBC rather than Android's SQLite. Dependency injection follows the same pattern, Hilt on Android, its Dagger core on the desktop, both 2.52. PDF generation is the one place the platform APIs genuinely differ: the desktop draws its fee challans and report exports with Apache PDFBox, while the phones use Android's own PdfDocument, so that capability lives once per platform rather than as shared code.

Service addresses and keys are supplied through protected build configuration, they are not in the report or the repository, and the messages shown to users name the action that failed without exposing a service address or request detail.

5. Testing and Evaluation

5. Introduction

Because all six apps share one core of academic rules, most of the testing effort points at that shared logic: a mistake in how attendance percentages, marks limits, or sync deltas are computed would show up in every app at once, so that is where a check earns its keep. The delta-sync logic, the part that decides what has changed since the last pull, carries the substantive automated coverage; the rest of the discipline is scenario-based. A per-screen registry lists, for each role and route, the states a screen has to handle correctly (loading, empty, error, validation, permission, offline), and that list is worked through against both the mobile and desktop builds to confirm the two platforms behave the same way from the same data.

The sections that follow take this in order: unit testing of the shared rules (§5.1), functional testing of the role workflows (§5.2), integration testing across the app-to-Supabase boundary (§5.3), and performance (§5.4), which is reported honestly as a local baseline on development hardware rather than a load test at scale. §5.5 draws the results together.

5.1 Unit Testing (UT)

The automated unit tests target the one piece of logic where a silent error would be both easy to make and hard to notice: incremental sync. Every app pulls only the rows that changed since its last successful sync, using a stored checkpoint (an updated_at watermark per owner, table, and scope), and then merges that delta into the local cache. Get the paging or the checkpoint advance slightly wrong and the app quietly misses records or re-applies stale ones, so this is the code that carries real unit coverage, in IncrementalSyncTest under core. The tests use a fake checkpoint store and a scripted fetch, so they run with no network and no database.

The domain validation rules, a midterm score in 0-25, a sessional in 0-15, an attendance register that must be complete before it locks, a mark edit that only an administrator other than the author may approve, are enforced in the shared core code and checked through the functional and parity testing in §5.2 rather than through separate unit tests. This is the honest state of coverage: unit testing is deliberately narrow, aimed at the sync engine, not a wide harness over every rule.

5.3 Integration Testing (IT)

Integration testing looks at the seams, the points where an app hands off to Supabase and where two apps meet through the shared database. Three of those seams matter most. Access control is not enforced in the app; it is enforced by Row-Level Security in Postgres, so the test that counts is whether the database itself refuses an out-of-role read or write even when a client asks for it. The second is the offline-first path: a record written in one app has to reach another app's cache correctly through the delta sync, without a manual refresh. The third is platform parity, the mobile and desktop builds share the same logic, and the per-screen scenario registry is the checklist that keeps their behaviour aligned.

To be clear about what was exercised where: RLS and the app-to-Supabase calls were checked against the live project with role-specific accounts; the delta-sync reconciliation has automated coverage over its logic (§5.1) and was confirmed end to end on the live data; and parity was verified by working the scenario registry against both builds by hand.

5.4 Performance Testing (PT)

Performance here is read against what the design actually tries to make fast, not against a load target. The apps are offline-first: a screen paints from the local Room cache first and refreshes in the background, and a refresh pulls only the rows that changed since the last checkpoint rather than the whole table (the delta sync described in §2.4.3 and covered by the unit tests in §5.1). 6. System Conversion

6. Introduction

There is no old system to migrate from, the college runs on paper registers, office files, and word of mouth today, so putting the CMS in place is a fresh rollout rather than a data cutover. That shifts what conversion actually means here: instead of moving records out of a legacy database, the work is standing up a clean backend, seeding it with trustworthy starting data, installing the six apps, and getting people used to a digital routine without disrupting a live term.

The system being rolled out is six apps over one shared backend. Three run on Android (admin, teacher, student, built with Jetpack Compose); three run on Windows (the same three roles, built with Compose Multiplatform on the JVM); and all six talk to a single Supabase project, Postgres through PostgREST, GoTrue for sign-in, Storage for files, edge functions for privileged actions, and Row-Level Security deciding who sees what. A role behaves the same whether someone is on their phone or at a desk, so a user can pick whichever device suits the moment.

This chapter walks through that rollout: the changeover method and why it was chosen (§6.1), deploying the apps and the Supabase project (§6.2), setting up the database schema when there is no legacy data to import (§6.2.1), training users on the real day-to-day flows (§6.2.2), the acceptance checks run after go-live (§6.3), the challenges that came with a multi-platform rollout (§6.4), and a short recap (§6.5).

6.1 Conversion Method

The plan is to start with a pilot in one department and expand from there. That department runs the system on a small, checked set of real records, and its admins, teachers, and students walk the whole journey, sign-in, attendance, marks, fees, notices, before any other department is switched on. Keeping the first group small is the whole point: fewer people to support while everyone is still learning, and any correction lands before it has to be made in a dozen places at once.

The two all-at-once options were weighed and set aside. A direct switch, every department live on day one, would pile record fixes, training, and support onto the same short window with no room to recover from a mistake. Running the paper process fully in parallel with the system would mean staff doing everything twice; the paper registers stay available as a fallback to check against during the pilot, but not as a second live system kept in lockstep. A pilot avoids both traps, and phased expansion then adds departments one at a time, only after the previous stage's issues are resolved and an acceptance check passes.

6.2 Deployment

Deployment has two halves that have to land in the right order: the shared Supabase backend comes up first, because every app is useless without it, and only then does each app get installed on the devices for its role. All six apps read and write the same college records through that one backend, so there is a single source of truth rather than six copies to keep in step.

The apps build from the nine-module Gradle project (settings.gradle.kts): three Android apps (mobile-admin, mobile-teacher, mobile-student) and three Compose-Multiplatform/JVM desktop apps (desktop-admin, desktop-teacher, desktop-student), all sitting on the shared core, mobile-shared, and desktop-shared modules. The Android apps package as APKs through the Android Gradle Plugin; the desktop apps package as Windows MSI installers through Compose Desktop's nativeDistributions. The toolchain is fixed, JDK 17, Kotlin 2.1.0, AGP 8.13.2, Gradle 8.13, so a build is reproducible rather than machine-dependent. One honest caveat: the current mobile artifacts are controlled test builds; signed release packaging and on-site install are part of the pilot, not something the build alone completes.

The backend is a single Supabase project. It carries the Postgres database reached through PostgREST, GoTrue for sign-in and session handling, two Storage buckets (exam-papers and photos), and the edge functions that run the privileged operations. Row-Level Security is what enforces access on every table, so a client can only ever read or write the rows its role owns. The project URL and keys live in protected build configuration, never in the repository.

6.2.1 Data Conversion

There is no old database to convert from, the starting records come off paper registers and office files. So "data conversion" here is really two jobs: build an empty, correctly-shaped database, then fill it with checked starting data. The shape comes first and comes from the migrations. The database schema is defined by the ordered SQL migrations under supabase/migrations/ (25 of them), applied in sequence from the base schema.sql through the Row-Level Security policies and later changes. Because the migrations are ordered and repeatable, the same run rebuilds the same schema every time, which is what makes a fresh project or a restored backup trustworthy.

With the schema in place, staff enter the actual college structure through the Admin apps, there is no legacy import to run, and no documents data to carry over (that feature was removed). Reference data (departments, the current academic session, fee heads) is entered first because everything else references it. Student rosters are the one bulk case: a roll-number-and-name list can be brought in from a CSV or XLSX file, and the parser skips any row missing a roll or name and flags duplicate rolls before the import is accepted. Everything is loaded under the same Row-Level Security that governs normal use, so nothing is written outside the loading admin's authority.

6.4 Challenges

The rollout's hard parts were mostly consequences of decisions made earlier in the project, and they are worth stating plainly rather than smoothing over.

The biggest was keeping six apps consistent. Three mobile and three desktop apps, each for a different role, could easily have drifted into six slightly different interpretations of the same rule. The response was to push the actual logic, validation, sync, the domain model, down into the shared core module so every app runs the same code, and to keep a per-screen parity checklist (the ParityScenarioRegistry) that lists the states each screen must handle so mobile and desktop can be checked against the same expectations. The tradeoff is that a change to shared code touches all six apps at once, which is exactly why it needed a checklist rather than trust.

Getting Row-Level Security right was the second. Enforcing access in the database instead of the client is the safer design, but it means every table needs a policy that is neither too open nor too tight, and a policy mistake fails quietly, you get back fewer rows, not an error. The policies were iterated per table and checked by trying out-of-role reads and writes and confirming the database refused them.

Offline-first sync was the third real tradeoff. Letting apps work from a local cache and reconcile later invites two classic bugs: losing a change, or applying it twice. The checkpoint-and-delta design pulls only what changed since the last watermark and advances that watermark only when the whole sync succeeds, so a failed sync re-pulls cleanly rather than half-applying, the behaviour the unit tests in §5.1 pin down.

The last was human, not technical. There is no legacy data to import, but there are also users who have never used a system like this. A pilot in one department, with training on the real attendance and challan flows, keeps that learning curve small and contained instead of hitting the whole college at once.

The most useful next steps come from two places: gaps that are genuinely thin today, and scope that was deliberately cut. None of the following is built, this is a prioritised list of what would add the most, not a preview of hidden features.

The clearest gap is testing. Automated coverage today is narrow, it covers the sync engine well and leaves the rest to manual scenario checks, so widening the automated suite over the domain rules (marks limits, attendance completeness, the mark-correction guard) is the highest-value work, because it protects every one of the six apps at once. Real push notifications are the next honest gap: notifications are currently rows the apps read under Row-Level Security and pick up on sync, not delivered by a push service, so a device only learns of a notice when it next refreshes. Adding true push would make time-sensitive notices land immediately. Beyond that sit the more optional additions, richer reporting and analytics past the current insights, the document-publishing feature that was withdrawn (FR-25/FR-26) if it is ever wanted back, and possibly extending to iOS or web, which the shared core makes plausible but which is a real amount of work.

Appendix B: General Coding Standards and Guidelines

The codebase follows a small set of conventions consistently, and they are worth stating as they actually appear in the source rather than as generic best-practice. The whole project is Kotlin under a single com.mbd.* package root, cmscommon for the shared code, and cmsadmin/cmsteacher/cmsstudent (with their desktop counterparts) for the apps. The architecture is layered MVVM with a repository boundary: the domain model, DTOs, and repositories live in the shared modules, screens observe view-models or controllers, and nothing in the UI reaches the database directly. Access control is deliberately not a coding standard the UI enforces, it is enforced by Row-Level Security in the database, so a screen that forgets a check still cannot read rows the role does not own.

Naming is regular enough to navigate by: types are PascalCase, members camelCase, and files carry their role as a suffix, Screen, ViewModel, Controller, Repository/RepositoryImpl, Dao, *Dto. Asynchronous work uses coroutines and Flow rather than callbacks, DTOs are kotlinx.serialization classes, local storage is Room entities and DAOs, and the UI is Jetpack Compose sharing one theme (ModernistColors in Theme.kt) across every app so the six look like one product.
