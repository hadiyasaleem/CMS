#### 3.3.3 Architecture Style and Module Mapping

The apps follow a layered MVVM / Repository pattern, so each concern can be reasoned about and changed on its own: a Compose screen presents information and takes input, a view model holds the screen's state and decides what the user is doing, a repository applies the shared rules and reads or writes data, and the Supabase backend stores the authoritative records. On Android, Hilt wires these pieces together. The client-server line runs between the apps — each with its own local cache — and that backend.

**Table 3-3 — Architecture Layer Mapping**

| Layer | Responsibility | Where it lives |
|---|---|---|
| Presentation (View) | Renders role-appropriate Compose screens, takes input, shows progress and feedback, and adapts to a phone or a desktop. | `mobile-shared` and `desktop-shared` UI kits; per-app screens in the six app modules |
| View model | Holds screen state and drives the steps for the selected task, without owning the business rules. | Each app module (`mobile-admin/teacher/student`, `desktop-admin/teacher/student`) |
| Repository + domain | Applies identity, validation, permission, academic, publishing, and reporting rules, and mediates between the local cache and the backend. | `core` (shared by all six apps) |
| Local cache | Keeps a role-scoped offline copy of the records the user may see and serves it when the network is down. | Room, via `mobile-shared` |
| Backend (data and services) | Stores the authoritative records and returns controlled results — Postgres through PostgREST, GoTrue for auth, Storage for files — with Row-Level Security enforcing access. | The Supabase project |
