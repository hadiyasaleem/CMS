### 3.7 Design Decisions

The main design choices follow from the college's roles, the sensitivity of academic records, and the need to support both classroom phone use and longer office work. Each is a standing choice with a reason and an accepted trade-off.

**Table 3-8 — Major Design Decisions**

| Design choice | Reason for the choice | Accepted trade-off |
|---|---|---|
| Separate Admin, Teacher, and Student apps, built from shared modules | Each role gets a smaller, clearer workspace, and sensitive admin actions stay out of student and teacher navigation; the apps reuse one shared component library and rule-set. | Six packages to build, test, and release — though only one library and one set of rules sit behind them. |
| A mobile and a desktop version of every role | Phones suit work during class and around campus; the desktop suits larger records, printing, and office tasks. | Each layout needs a device-specific arrangement even though the behaviour stays identical. |
| Access rules enforced in the database (Row-Level Security) | Confidential records stay protected even if a user bypasses a hidden screen or calls the backend directly — access is a property of the data, not just the UI. | Each new record type needs its access policies written and tested in the database. |
| One relational, normalised schema on Postgres with real foreign keys | Departments, sessions, subjects, students, and teaching records have explicit relationships and no duplicated facts; a mark cannot attach to a student who was never enrolled. | A report sometimes joins several related records before it can show a summary. |
| One shared source of truth, with an offline-first local cache | A record changed by an authorised user is what every permitted app sees, with no manual transfer; a Room cache keeps recent data usable on a weak connection, and sync pulls only what changed. | Confirming a new or changed record still needs a connection, and a few low-frequency screens need to be online. |
| Layered MVVM / Repository architecture | Presentation, role workflow, shared rules, and storage can each be understood and changed on their own. | A small action passes through several layers before it is confirmed. |
| Lock-then-approve for marks, with a single controlled write-path for GPA | A submitted mark cannot be changed silently, and a semester GPA is set only through one reviewed path — so results stay trustworthy. | A correction waits for an administrator, so it takes longer than a direct edit. |
| Status-based approvals for linking, corrections, and publication | Pending work and final decisions stay visible and auditable. | Work waits on an authorised reviewer. |
| In-app notifications only | Announcements reach the right audience inside the apps, without depending on an external push service or extra device permissions. | A user sees a notification the next time they open the app, not as a device push. |
| Administrative startup preparation | Core reference data loads when the Admin app opens, cutting repeated manual refreshes. | The first startup does more background work. |
| Native desktop file and print actions | Desktop users open, save, and print through familiar operating-system dialogs. | Those native windows follow the OS look, not the app's own design. |
