### 5.1 Unit Testing (UT)

The automated unit tests target the one piece of logic where a silent error would be both easy to make and hard to notice: incremental sync. Every app pulls only the rows that changed since its last successful sync, using a stored checkpoint (an `updated_at` watermark per owner, table, and scope), and then merges that delta into the local cache. Get the paging or the checkpoint advance slightly wrong and the app quietly misses records or re-applies stale ones — so this is the code that carries real unit coverage, in `IncrementalSyncTest` under `core`. The tests use a fake checkpoint store and a scripted fetch, so they run with no network and no database.

The domain validation rules — a midterm score in 0–25, a sessional in 0–15, an attendance register that must be complete before it locks, a mark edit that only an administrator other than the author may approve — are enforced in the shared `core` code and checked through the functional and parity testing in §5.2 rather than through separate unit tests. This is the honest state of coverage: unit testing is deliberately narrow, aimed at the sync engine, not a wide harness over every rule.

**Table 5-3 — UT-1: Paged delta fetch advances the checkpoint**

| Field | Detail |
|---|---|
| ID | UT-1 |
| Scenario | Fetch a change delta across several pages starting from the stored checkpoint |
| Input | A checkpoint at `10:00:00Z`; three rows returned over two pages (page size 2) |
| Expected | All three rows are returned in order; each page is requested from the inclusive checkpoint; the checkpoint advances once to the newest row's timestamp (`10:02:00Z`) |
| Result | Pass |

**Table 5-4 — UT-2: A failed sync leaves the checkpoint untouched**

| Field | Detail |
|---|---|
| ID | UT-2 |
| Scenario | A page fetch fails, or applying the delta to the local cache fails, part-way through a sync |
| Input | A stored checkpoint; a fetch (or a cache write) that throws on the second step |
| Expected | The error propagates; the checkpoint object is unchanged and never upserted, so the next sync safely re-pulls from the same point |
| Result | Pass |

**Table 5-5 — UT-3: Delta merge by stable key**

| Field | Detail |
|---|---|
| ID | UT-3 |
| Scenario | Merge a fetched delta into the existing cached rows, keyed on stable id |
| Input | Two cached rows; a delta that tombstones one, updates another, and adds a new one |
| Expected | The tombstoned row is dropped, the updated row keeps its newer timestamp, and the new row is added — the result reflects the delta, not a blind append |
| Result | Pass |
