### 3.1 Design Considerations

The design was shaped by the college environment: people move between office computers and personal phones, the internet is not always steady, and access to student information has to follow each person's role. The main considerations, and the response built into the design, are below.

**Table 3-1 — Design Considerations, Constraints, and Risks**

| Category | Consideration | Design response |
|---|---|---|
| Assumption | Each user has one authorised account and uses the app meant for their role. | Sign-in verifies the account, role, and status before opening a workspace. |
| Assumption | Sessions, subjects, teachers, and rosters are maintained by authorised staff. | Dependent features reuse those approved records instead of asking users to re-enter the same information. |
| Dependency | All six apps rely on one shared backend (Supabase). | Shared validation and row-level access rules keep records consistent whatever device is used. |
| Dependency | File uploads, password recovery, and account verification rely on managed storage and email. | A failed external operation is reported clearly and never leaves a false success. |
| Constraint | Mobile screens are small; desktop users expect wider working areas and native file/print actions. | The information and actions stay the same; only the presentation is arranged for each device. |
| Limitation | Live records need a connection to confirm and share; the apps are offline-first. | Each app shows its last-synced cache when offline, while new or changed records wait for a confirmed connection. |
| Risk | A wrong role or permission rule could expose confidential academic information. | Access is enforced centrally in the database with Row-Level Security, not merely hidden in the interface. |
| Risk | Two users update related academic information at nearly the same time. | An important update is validated against the latest record and rejected when the context is no longer valid. |
| Risk | Deleting a parent record (a department or session) could remove a great deal of dependent data. | Deletes cascade by design and are gated behind a confirmation dialog that names what will be removed. |
| Risk | A file upload or download is interrupted. | Progress, cancellation, and failure are reported, and the college record is left unchanged when the action is incomplete. |
| Risk | A large first-time load could delay the administrative home screen. | Essential admin data is prepared at startup and reused by later screens instead of manual refreshes. |
| Risk | The free-tier backend pauses after a spell of inactivity. | A scheduled keep-alive ping keeps the project awake between uses. |
