### 5.3 Integration Testing (IT)

Integration testing looks at the seams — the points where an app hands off to Supabase and where two apps meet through the shared database. Three of those seams matter most. Access control is not enforced in the app; it is enforced by Row-Level Security in Postgres, so the test that counts is whether the database itself refuses an out-of-role read or write even when a client asks for it. The second is the offline-first path: a record written in one app has to reach another app's cache correctly through the delta sync, without a manual refresh. The third is platform parity — the mobile and desktop builds share the same logic, and the per-screen scenario registry is the checklist that keeps their behaviour aligned.

To be clear about what was exercised where: RLS and the app-to-Supabase calls were checked against the live project with role-specific accounts; the delta-sync reconciliation has automated coverage over its logic (§5.1) and was confirmed end to end on the live data; and parity was verified by working the scenario registry against both builds by hand.

**Table 5-10 — IT-1: Row-Level Security blocks out-of-role access**

| Field | Detail |
|---|---|
| ID | IT-1 |
| Integration point | App → PostgREST/GoTrue, with RLS policies in Postgres |
| Scenario | A signed-in client attempts a read or write outside its role — an admin tries to write attendance; a student queries another student's marks |
| Expected | The database returns only rows the role owns and rejects the out-of-role write; the refusal comes from RLS, not from a client-side check that could be bypassed |
| Result | Pass |

**Table 5-11 — IT-2: A write in one app reaches another through sync**

| Field | Detail |
|---|---|
| ID | IT-2 |
| Integration point | Two apps ↔ shared Supabase tables ↔ local Room cache (delta sync) |
| Scenario | A teacher submits marks in one app; a student opens their result in another after the next sync |
| Expected | The change is pulled on the delta from the stored checkpoint and merged into the second app's cache; the student sees the new result without a manual reload, and a failed sync leaves the checkpoint unchanged so nothing is half-applied |
| Result | Pass |

**Table 5-12 — IT-3: Privileged operation runs only through an edge function**

| Field | Detail |
|---|---|
| ID | IT-3 |
| Integration point | Admin app → Supabase edge function (service-role) |
| Scenario | An action needing more authority than a signed-in request holds — create an account, change teacher status, promote or archive a session, revoke a student link |
| Expected | The operation succeeds only through the protected server-side function; the same action attempted as a direct client write is refused, keeping the elevated authority off the client |
| Result | Pass |
