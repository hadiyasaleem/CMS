#### 2.4.4 Security

The system's access rules live in the database, not in the apps: Row-Level Security on every table decides what each signed-in user may read and write, GoTrue handles authentication, and the few service-role operations run through edge functions that first verify the caller is an administrator. Connection secrets stay out of the repository. The requirements below are stated so each can be checked.

**Table 2-58 — Security Requirements**

| ID | Requirement | Applications | Priority |
|---|---|---|---|
| NFR-S1 | A user can see and do only what their authenticated role and current account status allow. | All six | High |
| NFR-S2 | A student sees only the records linked to their approved college identity, plus information published to an audience that includes them. | Student Mobile, Student Desktop | High |
| NFR-S3 | A teacher sees or changes only the students, classes, marks, attendance, and delegated duties tied to their assigned work and granted permissions. | Teacher Mobile, Teacher Desktop | High |
| NFR-S4 | Error messages, user-visible logs, and support text never reveal passwords, access tokens, personal secrets, database addresses, or full service-request URLs. | All six | High |
| NFR-S5 | After sign-out, protected screens and personal records are not reachable through back navigation or by reopening the app. | All six | High |
| NFR-S6 | Approval decisions and other sensitive changes keep a record of the responsible account, the action taken, and the time, for later review. | Admin and authorised Teacher apps | High |
| NFR-S7 | Sensitive write paths are constrained in the database itself: an administrator can read but never write attendance, a teacher records a GPA only through the controlled semester-result path, and a locked mark changes only through an approved correction. | All six | High |
