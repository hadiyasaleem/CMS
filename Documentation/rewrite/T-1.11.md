### 1.11 Project Planning

The work is planned in phases, each one a milestone that has to hold up before the next can build on it. The phases are defined by what depends on what, not by the calendar:

- **Foundation** — requirements and design, the shared data model and sign-in, and the academic structure (departments, sessions, subjects, and rosters) that every later feature attaches to.
- **Core academic operations** — attendance, timetables, marks entry with the lock-then-approve correction path, and semester results. These rest on the foundation, since a mark or an attendance row has to point at a real enrolled student.
- **Surrounding services** — fees and challans, fines, notices and notifications, the calendar, datesheets, exam-paper submission, and the Insights summaries drawn from the academic records.
- **Desktop parity** — the three desktop apps, reusing the shared logic to match the mobile apps feature for feature rather than re-implementing anything.
- **Verification and handover** — functional, integration, and performance testing across all six apps, college-data setup, and the report with its appendices.

Testing, data setup, and documentation are not held back for a final phase; they run against each milestone as it lands, so a phase counts as done only once its features are verified. Figure 1-1 lays out these phases and their milestones.
