### 7.3 Conclusion

The CMS takes a college running on paper registers and office files and replaces it with six role-based apps — admin, teacher, and student, each on Android and Windows — over one shared Supabase backend. The correlation below lines each objective up against the functionality that actually delivers it.

**Table 7-3 — Objective ↔ functionality correlation**

| Objective | Realising functionality | Outcome |
|---|---|---|
| One system across roles and devices | Six apps built from shared modules on one backend | Delivered |
| One authoritative record set | Single Supabase schema read by every app | Delivered |
| Digital attendance | On-screen register (Present/Absent/Leave, late flag) syncing to the other roles | Delivered |
| Protected mark changes | Lock-then-approve corrections via `mark_edit_requests` | Delivered |
| Personal academic access | Student overview: attendance, marks, results, timetable, fees, notices | Delivered |
| Role-scoped publication | Notices, calendar events, datesheets scoped by Row-Level Security | Delivered |
| Live admin summaries | Dashboard/insights drawn from the records, teacher views scoped | Delivered |
| Role-based security | Row-Level Security enforced in Postgres, not the client | Delivered |
| Mobile/desktop consistency | Shared `core` logic + the parity checklist | Delivered; field visual sign-off is pilot work |
| Verified before submission | Functional/integration scenario checks + unit coverage on sync | Partial — narrow automated coverage |

Two design choices carried most of the weight and are worth naming. Putting the domain logic in a shared `core` means all six apps compute the same rules from the same code — attendance percentages, marks limits, sync deltas — instead of six subtly different versions; keeping access control in Row-Level Security means a permission is enforced by the database itself, so a client bug cannot hand a user data they should not see. Those two decisions are what let a small team ship six coherent apps rather than six drifting ones.

It is also worth being straight about the limits. Automated testing is narrow — it covers the sync engine well, and the rest was checked as manual scenarios rather than a broad automated suite. Some scope was cut along the way: the document-publishing feature (FR-25/FR-26) was withdrawn rather than half-built. And the pilot deployment, real-user acceptance, and production-scale measurement are still ahead, not banked. What exists is a working, internally consistent system that meets its core objectives; what remains is the field validation that turns "works in the code" into "accepted at the college."
