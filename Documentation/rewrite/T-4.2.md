### 4.2 External APIs/SDKs

The six apps lean on a small, deliberately shared set of libraries rather than a different stack per platform. Everything to do with the backend — sign-in, reading and writing records, files, and the privileged server operations — goes through one client: the Supabase Kotlin SDK, version 3.1.4, pulling in its PostgREST, Auth (GoTrue), Storage, Realtime, and Functions modules from a single BOM. That SDK runs on Ktor 3.1.1 for the actual HTTP, and Kotlinx Serialization 1.8.0 turns records into JSON on the way out and back. There is no Firebase or FCM anywhere in the project; notifications are rows the apps read under their own access rules, not a push service.

Above that, the split is only where it has to be. The three phone apps draw their screens with Jetpack Compose (Material 3), the three Windows apps with Compose Multiplatform (Material 3) — the same declarative model, two runtimes. Both sides cache their data with Room so a workspace reopens with its last good records offline; the desktop build sits on a slightly newer Room (2.8.4) with the JVM bundled SQLite driver because it targets plain JDBC rather than Android's SQLite. Dependency injection follows the same pattern — Hilt on Android, its Dagger core on the desktop, both 2.52. PDF generation is the one place the platform APIs genuinely differ: the desktop draws its fee challans and report exports with Apache PDFBox, while the phones use Android's own `PdfDocument`, so that capability lives once per platform rather than as shared code.

Service addresses and keys are supplied through protected build configuration — they are not in the report or the repository — and the messages shown to users name the action that failed without exposing a service address or request detail.
