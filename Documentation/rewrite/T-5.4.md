### 5.4 Performance Testing (PT)

Performance here is read against what the design actually tries to make fast, not against a load target. The apps are offline-first: a screen paints from the local Room cache first and refreshes in the background, and a refresh pulls only the rows that changed since the last checkpoint rather than the whole table (the delta sync described in §2.4.3 and covered by the unit tests in §5.1). So the questions worth measuring are whether a cached screen opens without waiting on the network, and whether a refresh moves a small delta rather than everything.

These are indicative local baselines, measured on a single development machine and an Android emulator against representative sample data — a department, an academic session, a full roster, and a set of marks. They are not a benchmarked SLA. Real field figures — physical-device launch time, live college-network latency, and many simultaneous users — need production-sized data, connected devices, and the deployed service, and belong to pilot acceptance rather than being invented here.

**Table 5-13 — Performance Test Configuration**

| Item | Setting |
|---|---|
| Hardware | One development workstation; Android app on an emulator |
| Sample data | A department, one session, a full student roster, and recorded marks/attendance |
| What is measured | Cached-screen open, delta-sync payload size, and list responsiveness — as relative observations |
| Status of figures | Indicative local baseline, not a benchmarked SLA |
| Explicitly excluded | Physical-device startup, live-network latency, concurrent-user load |

**Table 5-14 — PT-1: Offline-first screen open and delta refresh**

| Field | Detail |
|---|---|
| ID | PT-1 |
| Aspect | How quickly a screen becomes usable, and how much a refresh transfers |
| Setup | Open a data-heavy screen (roster, records) with the cache already populated, then trigger a refresh after changing one record on the server |
| Observation | The screen renders from the Room cache without waiting on the network; the refresh pulls only the changed row from the stored checkpoint, not the full table, and a failed refresh leaves the last good view in place |
| Result | Meets the offline-first goal (indicative) |

**Table 5-15 — PT-2: List rendering and repeated navigation**

| Field | Detail |
|---|---|
| ID | PT-2 |
| Aspect | UI responsiveness on long lists and back-and-forth navigation |
| Setup | Scroll a full roster/records list and move repeatedly between screens in a role workspace |
| Observation | Lists render lazily and stay smooth because the data is already local; moving between screens re-reads from the cache rather than re-fetching, so navigation stays responsive |
| Result | Meets the responsiveness goal (indicative) |
