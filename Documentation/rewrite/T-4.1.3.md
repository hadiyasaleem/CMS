#### 4.1.3 Validate a Timetable Period

Adding a period to a session's timetable has to avoid two clashes: the same teacher, or the same room, booked over the same time on the same day. The check runs in the app and — decisively — as a **BEFORE trigger in the database**, so a conflict is caught even if two edits race. Only lecture periods are checked; breaks, zero periods, and a merged lecture (one row serving several sessions) are exempt. Rooms are picked from the managed buildings-and-rooms lists.

**Algorithm 3 — Validate a timetable period**
- *Input:* session, day, start/end time, teacher, room, and effective dates
- *Output:* the saved period, or a clear conflict message
- *Cost:* O(P) over the P relevant periods on that day

1. Start when a timetable period is submitted.
2. If the start time is not before the end time, reject the period and stop.
3. For each existing lecture on the same day whose effective dates overlap (a null date means unbounded):
   a. If its teacher matches and the times overlap, reject with the teacher conflict and stop.
   b. If its room matches and the times overlap, reject with the room conflict and stop.
4. Check that the session does not already hold the same slot.
5. Save the period, attach any approved shared sessions (a merged lecture), confirm, and stop.

Time overlap is half-open — two periods clash when one starts before the other ends and vice versa.
