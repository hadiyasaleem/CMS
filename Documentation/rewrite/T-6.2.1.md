#### 6.2.1 Data Conversion

There is no old database to convert from — the starting records come off paper registers and office files. So "data conversion" here is really two jobs: build an empty, correctly-shaped database, then fill it with checked starting data. The shape comes first and comes from the migrations. The database schema is defined by the ordered SQL migrations under `supabase/migrations/` (25 of them), applied in sequence from the base `schema.sql` through the Row-Level Security policies and later changes. Because the migrations are ordered and repeatable, the same run rebuilds the same schema every time, which is what makes a fresh project or a restored backup trustworthy.

With the schema in place, staff enter the actual college structure through the Admin apps — there is no legacy import to run, and no `documents` data to carry over (that feature was removed). Reference data (departments, the current academic session, fee heads) is entered first because everything else references it. Student rosters are the one bulk case: a roll-number-and-name list can be brought in from a CSV or XLSX file, and the parser skips any row missing a roll or name and flags duplicate rolls before the import is accepted. Everything is loaded under the same Row-Level Security that governs normal use, so nothing is written outside the loading admin's authority.

**Table 6-4 — Data conversion steps and controls**

| Step | Action | Control / safeguard |
|---|---|---|
| 1. Build the schema | Apply the 25 ordered migrations to the Supabase project | Migrations are ordered and repeatable — the same run yields the same schema; a failed run stops rather than half-applying |
| 2. Seed reference data | Enter departments, the academic session, and fee heads in the Admin apps | Compare totals against the approved college list before dependent data is added |
| 3. Create staff accounts | Create authorised admin and teacher accounts with role, department, and status | The office confirms identity, role, and active status; privileged creation runs through the edge function, not a direct write |
| 4. Load student rosters | Import a roll+name list from CSV/XLSX, or enter students individually | Rows missing a roll or name are skipped and duplicate rolls flagged before acceptance; the final roster count is reconciled |
| 5. Enter curriculum & timetable | Add courses, teaching assignments, rooms, periods, and weekly schedules | A clash is refused at write time by the database trigger; staff compare a sample and the full timetable against the signed plan |
| 6. Enter opening records | Where needed, enter verified starting attendance and marks before the pilot | Teachers and the department confirm totals and sampled student records; marks stay within their maxima (25/15) |

*Data protection during load:* a managed Postgres backup is taken before loading; afterwards, totals and sampled records are checked against the signed sources, accepted data is backed up, and a serious failure restores the last good backup.
