#### 3.5.3 Common Feedback and Interaction Rules

Because every screen is assembled from the same component library, these feedback rules hold the same way across all six apps.

**Table 3-7 — Common Interface Feedback**

| Situation | Feedback provided across the six applications |
|---|---|
| Loading | Skeleton placeholders for lists and tables (a spinner for a first detail load) instead of blank space; a pull-to-refresh shows a slim progress bar over the existing content. |
| Empty | An empty-state panel explains that there are no records and, for authorised users, offers the action to create the first one. |
| Filtered-empty | When a search or filter matches nothing, the screen says so and offers to clear the filters — kept distinct from having no records at all. |
| Validation | The affected field and a plain-language correction are shown before submission, not after the whole form is rejected. |
| Success | A snackbar confirms the action and the visible information updates in place. |
| Connection failure | An offline banner explains that the sync did not complete and offers a retry; the last-synced cached data stays on screen, and no service address is shown. |
| Permission restriction | An action the role does not hold is hidden or disabled, and any direct attempt returns a clear access message. |
| Destructive action | A confirmation names the record and spells out the effect — including a cascade summary, such as how many dependent records go with it — before a delete, rejection, disable, or unlink. |
| Back and refresh | The top bar gives predictable back navigation and a refresh where live information may have changed. |
