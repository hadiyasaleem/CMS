### 5.2 Functional Testing (FT)

Functional testing works through the role workflows end to end — the paths a real admin, teacher, or student actually takes — and confirms the visible result matches the rule behind it. These are scenario checks run against controlled sample data (a prepared department, session, roster, and marks) rather than automated tests, so each one records its steps and its pass condition and can be repeated from the same starting data. The four below span the three roles and the requirements they trace to; the same shared logic sits under both the mobile and desktop builds, so a case that passes on one platform is confirmed on the other through the parity checklist.

**Table 5-6 — FT-1: Sign in and role routing** *(FR-1)*

| Field | Detail |
|---|---|
| ID | FT-1 |
| Scenario | A user signs in and lands in the workspace for their role |
| Steps | 1. Enter valid credentials. 2. Submit sign-in. 3. Observe the landing workspace. |
| Expected | The session is verified and the user is routed to their own role's home — admin, teacher, or student — with only the screens and data that role may see; a wrong credential is refused with a plain message and no routing. |
| Result | Pass |

**Table 5-7 — FT-2: Record attendance** *(FR-10)*

| Field | Detail |
|---|---|
| ID | FT-2 |
| Scenario | A teacher marks a class register for a scheduled period |
| Steps | 1. Open an assigned class. 2. Mark each student PRESENT, ABSENT, or LEAVE, setting the late flag where needed. 3. Submit the register. |
| Expected | Every student must carry a status before the register submits; a late student is saved as present with the `is_late` flag, not as a separate status; the saved register reappears correctly in attendance history. |
| Result | Pass |

**Table 5-8 — FT-3: Enter marks, then correct a locked mark** *(FR-12 / FR-13 / FR-14)*

| Field | Detail |
|---|---|
| ID | FT-3 |
| Scenario | A teacher submits marks, then raises a correction that an administrator decides |
| Steps | 1. Enter midterm (0–25) or sessional (0–15) scores for the roster and submit. 2. Attempt to change a submitted score. 3. Raise a correction request with a reason. 4. As a different administrator, approve it. |
| Expected | Out-of-range or non-numeric scores are refused at entry; a submitted mark is locked and cannot be edited directly; the correction is applied only after an administrator — never the teacher who raised it — approves, and the original is retained until then. |
| Result | Pass |

**Table 5-9 — FT-4: Link a student account** *(FR-27 / FR-28)*

| Field | Detail |
|---|---|
| ID | FT-4 |
| Scenario | A student claims a roll number and an administrator approves the link |
| Steps | 1. As a registered student, claim an unclaimed roll in the session and submit identity details. 2. As an administrator, review the pending request. 3. Approve the matching request. |
| Expected | The student sees no academic data until approval; the admin sees only the claimed roll and matching identity; approval links exactly one account to one record and, if that record was linked before, downgrades the previous stale link so only one live link remains. |
| Result | Pass |
