### 6.3 Post Deployment Testing

Once the pilot department is running on real accounts, devices, and the deployed Supabase project, the system is checked again — this time end to end, against things development testing cannot stand in for: real sign-ins, a live network, and actual college records. These are manual acceptance checks, each a plain pass/fail criterion tied to a requirement, and each result is signed off at the college rather than assumed here in advance.

**Table 6-6 — Pilot post-deployment acceptance checks**

| Check | Acceptance criterion | Result |
|---|---|---|
| Sign-in and role routing *(FR-1)* | A valid sign-in lands each user in their own role's workspace; a wrong credential is refused | To sign off at pilot |
| Access scoping *(RLS)* | Each role sees only the rows it owns — a student cannot read another student's records, an admin cannot write attendance — enforced by the database, not the client | To sign off at pilot |
| Record attendance *(FR-10)* | A teacher marks a full register (Present/Absent/Leave, late flag), submits, and the saved register reappears in history | To sign off at pilot |
| Enter marks and correct one *(FR-12/13/14)* | Scores save within their maxima (midterm /25, sessional /15) and lock; a correction is applied only after a different administrator approves it | To sign off at pilot |
| Generate the fee challan *(FR-21)* | The desktop app produces a correct three-copy challan PDF (student/college/clerk) and saves or prints it through the native dialog | To sign off at pilot |
| Cross-app sync *(FR-24)* | A record written in one app appears in another after the next sync, without a manual reload | To sign off at pilot |

The checks are deliberately the workflows that matter most day to day, not an exhaustive pass over every screen. Customer-site execution and formal sign-off are pilot activities; the table above is the acceptance procedure to run there, with results recorded against each criterion.
